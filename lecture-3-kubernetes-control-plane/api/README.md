# Вспомогательные сервисы shop

Это готовый материал для части 0. Один бинарник и один образ работают в двух
режимах: `APP_ROLE=api` и `APP_ROLE=worker`. Программирование здесь не предмет
лабораторной; Kubernetes-ресурсы этих сервисов находятся в `helm/shop`.

## Контракт

| Запрос | Результат |
| --- | --- |
| `GET /health` | `200 ok`; при `HEALTH_FAIL=true` — `503` |
| `GET /version` | Версия сборки и роль процесса |
| `GET /metrics` | Метрики Prometheus, доступны и при `HEALTH_FAIL=true` |
| `POST /order` | Только API: создаёт заказ, возвращает JSON и HTTP `201` |
| `GET /orders` | Только API: последние 100 заказов, JSON `{"orders": [...]}` |

Тело заказа: `{"item":"book","quantity":1}`. Пустой товар, количество вне
`1..1000`, неизвестные поля и некорректный JSON дают `400`.
До инициализации БД и при её недоступности операции с заказами дают `503`.
`/health` проверяет работоспособность HTTP-процесса и намеренный сбой, а не БД:
доступный `/health` сам по себе не подтверждает работоспособность shop целиком.

## Переменные окружения

| Имя | Значение |
| --- | --- |
| `DATABASE_URL` | Обязательно: PostgreSQL DSN. В Kubernetes источник — Secret оператора |
| `APP_ROLE` | `api` по умолчанию, либо `worker` |
| `LISTEN_ADDR` | `:8080` по умолчанию, для обеих ролей |
| `HEALTH_FAIL` | `false` по умолчанию; читается при запуске процесса |
| `POLL_INTERVAL` | `1s` по умолчанию; интервал работы worker |

Каждая реплика использует пул максимум из пяти подключений. Таблица создаётся
автоматически с транзакционной advisory-блокировкой, чтобы одновременный старт
API и worker не приводил к гонке создания схемы. Worker забирают до 20 заказов
одним SQL-запросом с `FOR UPDATE SKIP LOCKED` и отмечают их обработанными.
Обработка в этом учебном сервисе — только изменение строки в БД, без внешних
платежей или других побочных эффектов. При потере соединения процессы остаются
живы и повторяют операции; заказы хранятся в PostgreSQL, не в памяти API.

## Сборка

Из каталога `lecture-3-kubernetes-control-plane`:

```bash
python3 scripts/setup-shop.py
```

Единый установщик собирает обе версии, разворачивает shop и подключает мониторинг.
Нужна готовая лабораторная 2; подробнее в [инструкции](../README.md#2-как-повторить-развёртывание). Он использует тот же Docker daemon, но временную
пустую registry-конфигурацию, чтобы публичная сборка не зависела от
`docker-credential-desktop`. Глобальный Docker config не меняется. Это важно
для текущего окружения: обычная сборка ожидала credential helper.

Эквивалент при исправно работающем credential helper:

```bash
docker build --build-arg VERSION=0.1.0 -t ghcr.io/itmo-labs/shop:0.1.0 api
docker build --build-arg VERSION=0.2.0 -t ghcr.io/itmo-labs/shop:0.2.0 api
```

Это два локальных образа с разной встроенной версией. Функциональность одинакова;
второй образ нужен для наблюдаемой смены версии процесса при обновлении.
Проверить версию можно через `/version` или заголовок `X-Shop-Version`.
Название `ghcr.io/itmo-labs/shop` — учебный локальный тег: публикация в GHCR не
выполнялась, существование такого удалённого образа не предполагается.

Образ запускается от UID/GID `65532`, содержит статический бинарник и корневые
сертификаты. В нём нет shell, поэтому `kubectl exec ... -- sh` не подходит для
диагностики приложения. Используй HTTP, логи и отдельные диагностические средства.

## Автоматическая проверка приложения

Единый установщик в конце создаёт заказ через API и ждёт `processed=true`,
проверяет пять targets Prometheus, три загруженных правила и dashboard Grafana.
Так проверяется путь API → PostgreSQL → worker в установленном Kubernetes.
При запуске с `--no-port-forward` эти проверки также выполняются, после чего
процесс завершается.

При наличии Go доступны проверки исходников:

```bash
cd api
go test -race ./...
go vet ./...
```

## Метрики для последующей работы

| Метрика | Смысл |
| --- | --- |
| `shop_http_requests_total{method,route,code}` | Запросы к зарегистрированным endpoint, кроме `/metrics` |
| `shop_http_request_duration_seconds` | Гистограмма длительности запросов |
| `shop_orders_created_total` | Заказы, созданные конкретной репликой API |
| `shop_worker_processed_orders_total` | Заказы, обработанные конкретным worker |
| `shop_worker_errors_total` | Ошибки SQL-операций worker после инициализации схемы |
| `shop_pending_orders` | Число необработанных заказов во всей БД; публикуется worker |
| `shop_database_up` | Успех последней операции с БД; до первой успешной операции — 0 |
| `shop_schema_ready` | Инициализация схемы прошла хотя бы один раз |
| `shop_build_info{version,role}` | Версия и роль процесса |

`shop_pending_orders` нельзя суммировать по worker: каждая реплика наблюдает
одну очередь. `shop_database_up` — последнее наблюдение, а не непрерывный probe;
у API без трафика значение может устареть. При ошибке чтения очереди её прежнее
значение тоже может устареть. Счётчики процесса сбрасываются при его рестарте.

Драйвер: [pgx, адаптер database/sql](https://pkg.go.dev/github.com/jackc/pgx/v5/stdlib).
