# Исходная нагрузка на заказы

Из корня репозитория, после установки `k6`:

```bash
SUMMARY_PATH=solutions/lab-4/evidence/part-3-load-summary.json \
  k6 run solutions/lab-4/load/orders.js
```

За 15 минут сценарий планирует 9000 запросов POST `/order`: 10 в секунду, каждый создаёт настоящий заказ. Успех — HTTP 201 с числовым ID. Worker обрабатывает заказы обычным способом; запросы GET `/orders` в нагрузку не входят.

Параметры можно менять через `BASE_URL`, `RATE` и `DURATION`. Для исходного замера оставляем значения по умолчанию и текущие ресурсы chart. Во время замера не выполняем обновления shop, чтобы не смешивать разные конфигурации.

Используется `constant-arrival-rate`: замедление ответов само по себе не снижает запланированную частоту запросов. Когда не хватает даже 50 VU, k6 пропускает итерации и считает `dropped_iterations`; это нужно учитывать рядом с ошибками и latency. Итоговый JSON сохраняет полный summary, параметры и время завершения. Исходные замеры сохранены отдельно от контрольных прогонов SLA.

Пятнадцатиминутная история подходит для учебного сравнения на этом стенде. Она не показывает суточные пики и не заменяет длительного наблюдения при выборе ресурсов рабочего сервиса.

## Контроль SLA

Перед контрольными прогонами согласованы критерии для 10 запросов/с: p95 HTTP POST `/order` ≤300 мс, доля успешных заказов ≥99,5%, пропущенных итераций 0. Успех — HTTP 201 с положительным целочисленным ID; срок фоновой обработки worker в эту latency не входит. Условия добавлены в k6 thresholds: превышение делает exit code ненулевым, summary сохраняет `sla_passed` и сами границы.

Это критерии короткого учебного испытания, а не подтверждение месячного SLA. Старые summaries не переписываются задним числом; контрольные результаты имеют отдельные имена с префиксом `part-8-`.
