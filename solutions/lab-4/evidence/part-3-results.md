# Исходный замер и рекомендации

29 октября 2026 года, 15:01:50–15:16:50 UTC, POST `/order`, 10 запросов в секунду. Создан 9001 заказ, ошибок и пропущенных итераций нет. HTTP p95 — 6,33 мс, p99 — 30,04 мс, максимум — 1245,95 мс. Это latency HTTP-запроса создания заказа; время фоновой обработки worker сюда не входит.

[Полный результат k6](part-3-load-summary.json). По данным Prometheus на конец нагрузки очередь пуста, прирост счётчика ошибок worker равен нулю. [Запросы и результаты](part-3-prometheus-baseline.json). `increase()` экстраполирует счётчики между scrape, поэтому его дробные значения не используем для точного подсчёта заказов.

На нагруженном пятнадцатиминутном интервале наблюдались:

| Компонент | CPU p95 по минутному rate | Пик working set |
| --- | ---: | ---: |
| API, диапазон между репликами | 3,4–6,1m | 13,2–14,0 MiB |
| Worker, диапазон между репликами | 2,7–2,8m | 12,8 MiB |
| PostgreSQL | 41,0m | 73,3 MiB |
| Batch | 250,2m | 38,5 MiB |

Стратегия krr `simple` использовала час истории, шаг 30 секунд, CPU p95 и пик памяти +15%. Её окно включает как нагрузку, так и соседний простой, поэтому числа CPU не обязаны совпасть с отдельной выборкой в таблице выше. Применяются стандартные нижние границы: 10m CPU и 100 MiB памяти.

| Компонент | Было CPU request / limit | krr CPU request / limit | Было memory request / limit | krr memory request / limit |
| --- | --- | --- | --- | --- |
| API | 25m / 250m | 10m / не задан | 32Mi / 128Mi | 100Mi / 100Mi |
| Worker | 25m / 250m | 10m / не задан | 32Mi / 128Mi | 100Mi / 100Mi |
| PostgreSQL | 100m / 500m | 26m / не задан | 128Mi / 512Mi | 100Mi / 100Mi |
| Batch | 50m / 250m | 251m / не задан | 64Mi / 128Mi | 100Mi / 100Mi |

Память API в рекомендации выше исходного request из-за нижней границы 100 MiB. По замеру приложение столько не потребляло. Значение CPU batch около 250m отражает уже действующую квоту; оно не доказывает, что процессу достаточно четверти ядра без замедления.

[Штатный отчёт](part-3-krr-native.json) включает только Deployment. [Отчёт с CNPG](part-3-krr-cnpg.json) дополнительно содержит PostgreSQL как `Cluster`: адаптер добавляет обнаружение ресурса, расчёт выполняет сам krr. [Порядок запуска и ограничения](../platform/krr.md).

Через Helm upgrade, revision 4, применены CPU requests и memory request/limit из krr. CPU limits сохранены прежними: API и worker — 250m, PostgreSQL — 500m, потому что политика `shop-require-resources` требует наличия обоих limits. Эти CPU limits не выдаём за рекомендации krr. Batch оставлен с исходными параметрами как управляемый источник нагрузки.

В Pod подтверждены новые ресурсы, PostgreSQL Ready. Все семь Pod сохраняют Burstable QoS: CPU request меньше CPU limit, хотя у API, worker и PostgreSQL память request/limit уже равна.
