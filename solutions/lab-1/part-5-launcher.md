# Часть 5: сборка единого запускателя

Начато 26 октября 2026 года после верных ответов по seccomp. Цель части — объединить освоенные механизмы в `mydocker.sh`, проверить API и сравнить с запуском через Docker. Оболочка, единый запуск API и понимание порядка сборки подтверждены; текущий шаг — сравнение с Docker.

## Шаг 5.1: ограниченная группа и изолированная оболочка — выполнено

Первая версия [mydocker.sh](mydocker.sh) создавала или переиспользовала пустую собственную cgroup `lab1-mydocker`, задавала `memory.max = 67108864`, `memory.swap.max = 0`, `cpu.max = 50000 100000`, `pids.max = 32` и открывала оболочку. Заполненная группа отвергается до изменения лимитов. Запуск на macOS или запуск всего скрипта от root завершается отказом. Ниже сохранена история проверки первой версии; актуальный скрипт уже запускает API по шагу 5.2.

Новая дочерняя оболочка с помощью sudo записывает собственный PID в `cgroup.procs`, возвращается к UID/GID вызывающего пользователя через setpriv и создаёт шесть namespaces. Процессы создаются уже в ограниченной группе и наследуют её. Управляющая оболочка остаётся снаружи. Во внутренней оболочке UID будет 0 нового user namespace; удаление capabilities предусмотрено после настройки окружения на следующем шаге. Пустая группа после выхода остаётся для продолжения.

Смысл порядка: [наследование cgroup](https://docs.kernel.org/admin-guide/cgroup-v2.html#what-is-cgroup), [создание namespaces](https://man7.org/linux/man-pages/man1/unshare.1.html). Оболочка в новом PID namespace должна видеть PID 1; cgroup namespace на этом шаге не создаётся, поэтому путь `0::/lab1-mydocker` остаётся видимым внутри.

Предварительная read-only проверка VM: контроллеры memory/cpu/pids включены для дочерних групп, группа `lab1-mydocker` отсутствует. Старый API под seccomp ещё работает с PID 1105; студенту предложено остановить его Ctrl+C в терминале сервиса. Инструменты и файлы API/seccomp на месте. Подготовлены каркас и команды проверки; фактическое создание группы и запуск namespaces студентом ещё не подтверждены.

В обычной оболочке VM прочитать и запустить скрипт:

```sh
sed -n '1,160p' /tmp/lab1-mydocker.sh
bash /tmp/lab1-mydocker.sh
```

После успешного входа в новую `bash-5.2#`:

```sh
echo "shell PID=$$"
id
cat /proc/self/cgroup
cat /sys/fs/cgroup/lab1-mydocker/{memory.max,memory.swap.max,cpu.max,pids.max}
ps -eo pid,ppid,uid,comm
```

Ожидаются внутренний PID 1, UID 0, путь `0::/lab1-mydocker`, лимиты `67108864`, `0`, `50000 100000`, `32`. Студенту предложено прислать вывод и оставить изолированную оболочку открытой. При ошибке скрипта последующие команды внутри namespaces выполнять нельзя.

Результат получен: PID 1, UID 0, путь `0::/lab1-mydocker`, все четыре значения лимитов совпали. `ps` показал bash с PID 1 и ps с PID 5. Снимок и протокол — [шаг 5.1](evidence/part-5-shell.md). Старый API остановлен; активная оболочка остаётся в группе.

## Шаг 5.2: API одним запуском — подтверждено

В скрипт добавлена внутренняя точка входа `--inside`: она запускается unshare как PID 1, задаёт hostname `lab-api`, поднимает loopback, удаляет bounding/inheritable/ambient capabilities, задаёт no_new_privs, затем через Python-загрузчик устанавливает seccomp и заменяет процесс сервисом API. Настройка сети и hostname должна завершиться до удаления необходимых полномочий. Внешний UID остаётся UID вызывающего пользователя.

Пути API, загрузчика и профиля по умолчанию — ранее подготовленные файлы в `/tmp`. При переносе можно задать `LAB_API_BIN`, `LAB_SECCOMP_RUN`, `LAB_SECCOMP_PROFILE`. Требуются Bash, sudo, util-linux, iproute2, Python и libseccomp; это запускатель для подготовленной Linux VM, а не переносимый образ файловой системы.

Добавлен `unshare --kill-child`: при завершении внешнего unshare его ещё живой потомок будет завершён. Группа остаётся для чтения счётчиков; повторный запуск разрешается только после её опустошения. Синтаксис обновлённого файла и совпадение контрольных сумм копии в VM проверены. Новый запуск инфраструктуры ассистентом не выполнялся.

В текущей `bash-5.2#` завершить оболочку шага 5.1:

```sh
exit
```

В вернувшейся обычной оболочке VM прочитать обновлённый файл и запустить:

```sh
sed -n '1,180p' /tmp/lab1-mydocker.sh
bash /tmp/lab1-mydocker.sh
```

Оставить сервис в переднем плане. Во втором терминале обычной VM выполнить:

```sh
lab_pid=$(pgrep -u 501 -x lab1-api)
if [[ "$lab_pid" =~ ^[0-9]+$ ]] &&
   [[ "$(cat "/proc/$lab_pid/cgroup")" == '0::/lab1-mydocker' ]]; then
  ps -p "$lab_pid" -o pid,uid,args
  grep -E '^(NSpid|Cap(Inh|Prm|Eff|Bnd|Amb)|NoNewPrivs|Seccomp|Seccomp_filters):' "/proc/$lab_pid/status"
  cat "/proc/$lab_pid/cgroup"
  cat /sys/fs/cgroup/lab1-mydocker/{memory.max,memory.swap.max,cpu.max,pids.max}
  sudo nsenter -t "$lab_pid" --uts hostname
  sudo nsenter -t "$lab_pid" --net \
    curl --noproxy '*' --max-time 3 -i http://127.0.0.1:18080/health
else
  printf 'Один API в lab1-mydocker не найден; PID: %s\n' "$lab_pid"
fi
```

Результат получен 26 октября: внешний PID 1260, UID 501, `NSpid: 1260 1`, все пять Cap-наборов нулевые, `NoNewPrivs = 1`, `Seccomp = 2`, один фильтр. Путь cgroup и все четыре лимита совпали. Hostname `lab-api`, `/health` вернул HTTP 200 с `ok`. Протокол и снимок — [единый запуск API](evidence/part-5-mydocker-api.md). Стартовый лог на этом снимке не показан; внутренний PID 1 подтверждён через NSpid. API работает, остановка не подтверждена.

## Понимание порядка сборки — проверено

1. Почему hostname и loopback настраиваются до удаления capabilities?
2. Почему cgroup назначаем до unshare/fork, а не переносим уже запущенный API?

26 октября студент верно ответил: после удаления capabilities уже не хватит полномочий для настройки hostname/сети; помещение процесса в cgroup до unshare/fork обеспечивает наследование группы всеми потомками и применение лимитов с начала запуска. Оба ответа без ошибок. Сборка запускателя и эта проверка понимания завершены.

Далее выполнено [сравнение с Docker](part-5-docker-compare.md): Docker-контейнер запущен студентом, настройки и HTTP 200 подтверждены. Различия rootfs, UID mapping, cgroup namespace и управления описаны. Финальные ответы по сравнению верны; часть 5 завершена 26 октября 2026 года.
