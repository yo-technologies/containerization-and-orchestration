# Часть 3: ограничение создания задач через pids.max

Источник: снимок терминала студента от 22 сентября 2026 года. Выполнен ограниченный fork-тест из основного отчёта. Перед запуском проверены `pids.max = 32` и пустая группа; запускающая оболочка помещена в `lab1-pids`, затем через `exec setpriv` запущен stress-ng от UID 501/GID 1000. Дочерние процессы наследовали группу.

Начальные значения — см. [протокол подготовки](part-3-pids-baseline.md): `pids.current = 0`, `pids.peak = 0`, `pids.events:max = 0`.

## Вывод нагрузки

stress-ng с PID 2541 сообщил:

```text
setting to a 5 secs run per stressor
dispatching hogs: 1 fork
skipped: 0
passed: 1: fork (1)
failed: 0
metrics untrustworthy: 0
successful run completed in 4.83 secs
```

Строка метрик `fork`:

| Метрика stress-ng | Значение |
| --- | ---: |
| bogo ops | 27420 |
| real time (secs) | 4.82 |
| usr time (secs) | 2.51 |

| bogo ops/s (real time) | 5683.56 |
| bogo ops/s (usr+sys time) | 3790.38 |

## Счётчики после завершения

Последовательное чтение `pids.current`, `pids.peak`, `pids.events`, `cgroup.procs` дало:

```text
0
32
max 31075
```

`cgroup.procs` не вывел PID. Управляющая оболочка осталась доступна.

## Вывод

Пик одновременно учитываемых задач достиг 32. `pids.events:max` вырос с 0 до 31075, что подтверждает отклонение попыток создать задачи сверх лимита. После завершения `pids.current` вернулся к 0, а список живых процессов группы пуст — нагрузка не осталась запущенной.

Лимит касается одновременно учитываемых задач, не суммарного количества операций за всё время. Поэтому 27420 условных операций stress-ng не противоречат лимиту 32. `passed: 1` также не отменяет срабатывание ограничения: stress-ng штатно обработал ситуацию и завершил свой тест, а отказы фиксирует контроллер в `pids.events`. Сами численные коды возврата отдельных `fork` на снимке не показаны; вывод об ограничении основан на счётчике cgroup. Семантика: [PID controller](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid).

Практический опыт с pids подтверждён. Проверка понимания пройдена 22 сентября 2026 года после уточнений: лимит не означает строго последовательное выполнение; освободившееся место позволяет создать новую задачу, а ранее созданный потомок остаётся в группе A при переносе родителя в B. Оба уточняющих ответа студента верны. Следующий шаг — исходное состояние capabilities; его результаты в данный протокол не входят.
