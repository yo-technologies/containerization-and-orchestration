# Выбор трёх метрик для алертов

26 октября 2026 года студент выбрал три сигнала и объяснил их назначение. Проверка понимания пройдена: почти 100% throttled periods означает исчерпание квоты во многих периодах, а не почти полное отсутствие CPU-времени.

| Выбранный сигнал | Что обнаруживает | Почему это важно |
| --- | --- | --- |
| Память относительно memory.max | Приближение учитываемой памяти cgroup к её потолку | Даёт возможность заметить риск OOM до убийства процесса. Отношение к лимиту сопоставимо при разных размерах групп. |
| Доля CPU-периодов с throttling | Частое исчерпание CPU-квоты данной группы | Указывает, что спрос на CPU упирается в заданную квоту; это может увеличивать задержки. Высокое значение не доказывает нехватку CPU всего хоста и не равно доле времени без CPU. |
| Новые события oom_kill | Ядро убило процесс при OOM в cgroup | Это уже произошедший отказ, после которого сервис мог стать недоступен. Нужна отдельная проверка /health, поскольку убийство процесса в многопроцессной группе не всегда означает остановку всего сервиса. |

## Представление сигналов в Prometheus

Память относительно лимита — gauge-отношение:

```promql
lab1_cgroup_memory_current_bytes{job="lab1-cgroup",cgroup="lab1-mydocker"}
/
lab1_cgroup_memory_limit_bytes{job="lab1-cgroup",cgroup="lab1-mydocker"}
```

Доля периодов с ограничением — отношение скоростей counters, в dashboard используется окно 1 минута:

```promql
rate(lab1_cgroup_cpu_throttled_periods_total{job="lab1-cgroup",cgroup="lab1-mydocker"}[1m])
/
rate(lab1_cgroup_cpu_periods_total{job="lab1-cgroup",cgroup="lab1-mydocker"}[1m])
```

Когда CPU-периоды не идут, отношение не определено; отсутствие значения не является доказательством нулевого throttling. Для рабочего алерта также важны наличие нагрузки и пользовательский эффект.

Для новых OOM kills нужен прирост counter за окно, например:

```promql
increase(lab1_cgroup_memory_oom_kills_total{job="lab1-cgroup",cgroup="lab1-mydocker"}[5m])
```

Абсолютное oom_kills_total > 0 оставалось бы истинным после старого инцидента до сброса группы. Прирост выделяет новые события; окно 5 минут здесь иллюстрирует запрос, а не согласованный порог алерта.

Числовые пороги, for и доставка новых уведомлений для ЛР1 не настраивались. По заданию части 8 требуется выбрать три метрики и обосновать их, что выполнено. Действующие прикладные правила ЛР2 сохранены; их наличие не выдаётся за установку новых ресурсных правил.

## Что подтвердил опыт

В [нагрузочном опыте](../evidence/part-8-load.md) память выросла примерно до 19,5 MiB из 64 MiB, CPU достиг 0,5 ядра, почти все новые периоды содержали throttling. OOM kills остался 0, /health работал перед штатной остановкой. [OOM части 3](../evidence/part-3-memory-oom.md) отдельно показал убийство API и потерю доступности. Это связывает выбранные сигналы с наблюдавшимися механизмами, не утверждая срабатывание новых алертов.
